# 로드맵 (ROADMAP)

이 문서는 term-consistency 의 버전별 마일스톤과 그 순서의 근거를 정의한다. **할 일 목록이 아니라 "왜 이 순서인가" 의 문서**다.

각 마일스톤은 (1) 끝났다는 기준 (DoD), (2) 다음 마일스톤에 어떻게 기여하는가, (3) 잘못되고 있다는 조기 경보 신호 — 이 세 가지를 함께 적는다.

원칙은 [PRINCIPLES.md](./PRINCIPLES.md), 현재 버전의 비스코프는 [SCOPE.md](./SCOPE.md), 회귀 픽스처 패턴은 [TESTING.md](./TESTING.md) 를 참조한다.

## 순서의 정당화 — 왜 이 사슬인가

각 마일스톤은 이전 것이 없으면 안전하게 진행할 수 없다. 가장 중요한 두 화살표:

1. **v0.2 (픽스처) → v0.3 (override).**
   레포별 용어집 override 는 매칭 결정 로직을 건드리는 변경이다. 안전하게 하려면 "변경 전후의 동작 비교" 가 자동화되어 있어야 한다 → 회귀 픽스처가 먼저 깔려야 한다.

2. **v0.3 (override) → v0.4 (PR 트리거).**
   PR 트리거는 도구의 출력을 자동으로 PR 댓글로 발행한다. v0.3 이전 단계의 도구는 false positive 를 다수 낸다 (예: pytorch-kr 의 "학습" → terms.kr "훈련" 충돌). 정확도가 갖춰지기 전에 자동화를 입히면 PR 댓글이 노이즈로 도배되어 가설 ("리뷰어 부담 경감") 자체가 망가진다.

이 두 화살표가 ROADMAP 의 척추다. 다른 작업 순서는 일정 조정 가능하지만, 위 두 의존은 어겨선 안 된다.

또 하나: **v1.0 (공개) 와 v1.1+ (타 레포 확장) 은 분리한다.** 같이 묶으면 공개 후 받은 피드백과 확장에서 생긴 새 버그가 섞여 추적이 불가능해진다. 변경 부채 동시 폭발 패턴의 전형 케이스이므로 의식적으로 분리한다.

   - 회귀 픽스처와는 다른 영역이므로 분리해서 도입 ([TESTING.md](./TESTING.md) 의 "운영 로그 / 관측성" 섹션 참조).
   - 형식 후보: 구조화 JSON 로그, 또는 Python `logging` 표준 라이브러리 + 적절한 formatter.

### Definition of Done

- [ ] 코멘트 노이즈 비율 (= [ERR] 비율 + false positive 비율) 이 v0.3 픽스처 베이스라인 대비 회귀 없음.
- [ ] 매 자동 실행이 운영 로그로 기록되어 사후 추적 가능.

## v1.1+ (확장 — 한 문단씩)

### 타 레포 확장

다른 한국어 번역 레포 (다른 OSS 조직의 번역 프로젝트) 로 확장. v0.3 에서 깐 어댑터 추상화 위에서 새 레포의 용어집 파서만 추가하면 되는 구조여야 한다. **v1.0 의 외부 피드백을 받은 후에 진행한다** — 가정 2 (각 레포에 자체 용어집 존재) 을 데이터로 검증한 다음.

### LLM 가이드라인 통합 (이슈 #3)

번역 가이드라인 (`TRANSLATION_GUIDE.md` 의 비-용어집 규칙) 을 LLM 으로 파싱해서 룰 형태로 변환. 원칙 1 (가볍다) 과 충돌 가능성 — "가이드라인 파싱" 은 1회성, "매 PR 검증" 은 룰베이스로 유지하면 원칙 위반 없이 가능하다. 이 분리가 가능한지가 이 마일스톤의 첫 검증 항목.

### 오타 검사 분리 (이슈 #4)

용어 일관성 도구가 아닌 별도 도구로 분리. ROADMAP 에 적되, 이 레포 안에서 진행하지 않는다.
