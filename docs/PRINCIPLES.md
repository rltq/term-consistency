# 설계 원칙 (PRINCIPLES)

이 문서는 term-consistency 가 어떤 도구이고, 어떤 도구가 *아닌지*를 결정짓는 3개의 원칙을 정의한다. 코드 변경, 새 기능 추가, 의존성 도입 — 모든 의사결정은 이 원칙들 위에서 정당화된다.

원칙은 **취향이 아니다.** 깰 수는 있지만, 깨는 순간 도구의 가설이 함께 흔들린다. 깰 거면 "깨고 싶을 때" 절차를 따른다 (문서 하단).

---

## 가설

> **PR 제출 전 룰베이스 스크리너가 번역 PR 리뷰어의 피로를 경감시킨다.**

이 가설이 참인지는 도구 자체가 가벼울 때, 인간 리뷰가 살아 있을 때, 출력이 행동 가능할 때만 의미가 있다. 아래 3개 원칙은 그 세 조건의 다른 이름이다.

가설이 거짓으로 드러나면 (예: 도구를 도입해도 리뷰어 부담이 줄지 않는다는 데이터), 원칙도 갈아엎어야 한다. 원칙은 가설의 종속 변수다.

---

## 원칙 1. 가볍다

> 검증은 LLM 없이, 룰/정규식 베이스로 한다. 모든 PR마다 기다림 없이 돌 수 있어야 한다.

**왜.** 번역량이 많아질 때 (수십~수백 hunk) 무거운 도구는 도입 자체가 안 된다. 도구가 PR 워크플로에 자연스럽게 끼어들려면 "느려서 안 쓰겠다"는 핑계를 만들지 않아야 한다.

**대가.** 정확도. 룰베이스는 문맥을 못 읽는다. → 원칙 2로 보완.

**위반 신호.**
- LLM 호출, 무거운 NLP 모델 의존성을 도입하는 PR
- "정확도를 위해" 외부 API에 의존하는 변경
- 단일 PR 처리에 수십 초 이상 걸리는 변경

**예외 조건.** 없음. 무거운 처리가 정말 필요하다면 별도 도구로 분리한다 (이슈 #4가 오타 검사를 분리한 것과 같은 이유).

---

## 원칙 2. 인간 리뷰가 마지막 결정자

> 도구는 사람을 대체하지 않는다. 의심스러운 경우 알리는 것이 침묵하는 것보다 낫다 — **FP > FN.**

**왜.** 도구의 가설은 "리뷰어 부담 경감"이지 "리뷰어 대체"가 아니다. 도구가 놓친 오류는 리뷰어가 잡을 수 없지만, 도구가 잘못 알린 케이스는 리뷰어가 거를 수 있다. 이 비대칭이 명확하다.

**대가.** 노이즈. 알림이 늘면 리뷰어가 도구 자체를 신뢰하지 않게 됨. → 원칙 3으로 보완.

**위반 신호.**
- "정확도 올리려고" 검사를 silent skip 하는 변경 (예: 코드블럭 안 내용을 그냥 무시)
- "이건 false positive 같으니 빼자"는 추론이 데이터 없이 들어감
- FN(놓침)을 줄이는 변경과 FP(오탐)를 줄이는 변경을 같은 PR에 섞음

**예외 조건.** silent skip이 정말로 필요하면, 그 결정을 `SCOPE.md`에 명시한다. 코드 안에 묻으면 안 된다.

**측정.** v0.2.0 에서 회귀 픽스처가 깔렸다. FP/FN 비율 추적의 기반이 있으며, PR 마다 스냅샷 diff 가 자연스러운 관측점이다. v0.3 작업 0 의 유닛 테스트 레이어 확장이 분기 경계까지 관측 범위를 넓힐 예정.

---

## 원칙 3. 출력은 근거다

> 매 알림은 두 청중에게 동시에 행동 가능해야 한다 — 기여자(수정 힌트)와 리뷰어(검증 근거).

**왜.** 알림이 "여기 뭔가 있다"로 끝나면 양쪽 다 추가 조사를 해야 한다. 그러면 도구의 가치가 0. 알림에 "어디서 / 무엇을 / 왜 의심하는가 / 무엇으로 바꿔야 하는가"가 다 있으면, 기여자는 바로 고치고 리뷰어는 바로 검증한다.

기여자가 고치기에 충분한 근거 = 리뷰어가 판단하기에 충분한 근거. 두 청중의 요구는 같은 정보 집합으로 수렴한다 — 이게 이 원칙을 하나로 묶을 수 있는 이유다.

**대가.** 출력 포맷의 복잡도. 단순 grep 같은 출력은 못 쓴다. → 모듈 분리(`find` / `format`)로 흡수.

**위반 신호.**
- `[ERR]` 같이 의미가 모호한 라벨 (v0.1.0의 실제 사례)
- 영문/한글 컨텍스트 중 한쪽만 보여주는 출력
- "왜 이 매칭이 떴는가"를 추적할 수 없는 결과
- 매칭의 근거가 출력에 빠지고 사용자가 main.py를 읽어야 이해되는 상황

**예외 조건.** 디버그 모드는 예외. 일반 사용자 출력은 항상 양쪽 청중을 동시에 만족시킨다.

## 원칙끼리 충돌할 때

세 원칙은 가끔 서로 당긴다:

- **1 vs 2:** 정확도(2)를 위해 무거운 처리(1 위반)를 도입하고 싶은 유혹.
- **2 vs 3:** FP를 줄이려고(2 보완 의도) 알림을 묶거나 줄이면 근거(3)가 함께 사라질 수 있음.
- **1 vs 3:** 풍부한 근거(3)를 위해 더 많은 분석(1 위반)이 필요할 수 있음.

**충돌 시 우선순위: 2 > 3 > 1.**

- **2가 최상위인 이유:** 깨지면 도구의 존재 이유가 사라짐.
- **3이 그 다음인 이유:** 2를 실현하는 수단. 인간 리뷰가 효율적이지 않으면 2의 가치가 약해진다.
- **1이 마지막인 이유:** 가벼움은 도구가 워크플로에 도입되기 위한 조건일 뿐, 그 자체가 목적은 아니다. 단, 1을 포기하면 도입 자체가 안 되어 결과적으로 2/3가 실현되지 못한다는 점을 기억할 것.

---

## 깨고 싶을 때

위 원칙 중 하나를 깨고 싶어진다면 다음 4단계를 밟는다:

1. **어느 원칙인지 명시한다.** 여러 개라면 모두.
2. **가설(맨 위)이 여전히 유효한지 다시 적는다.** 유효하지 않다면 가설부터 갱신한다.
3. **그 변경이 가설을 어떻게 강화/약화시키는지** 1문단으로 적는다.
4. **`ROADMAP.md`의 해당 버전 항목에 그 결정을 기록한다.** PR 본문이 아니라 ROADMAP에. 이후 변경 추적이 가능하도록.

원칙은 영구적이지 않다. 단, **무의식적으로 깨지면 안 된다.** 의식적으로 깨는 것과 잊고 깨는 것은 다른 종류의 변경이다.
