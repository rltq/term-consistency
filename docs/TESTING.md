# 테스트 (TESTING)

이 문서는 term-consistency 의 회귀 픽스처 패턴, 워크플로, GitHub 이슈 #9 (raw queue) 운영 방법을 정의한다. 운영 문서이므로 적힌 절차를 따라 실행했을 때 적힌 결과가 나와야 한다 — 안 나오면 코드 또는 이 문서가 거짓이다.

회귀 픽스처가 없는 변경은 ROADMAP 의 v0.2 부터 원칙적으로 금지된다. 이유: 회귀 검증 단위 없이 변경이 누적되면 변경 부채 동시 폭발 패턴이 발생한다.

---

## 용어

회귀 픽스처라는 용어가 생소할 수 있으므로 이 문서에서 사용하는 4개 용어를 먼저 정의한다.

**회귀 픽스처 (regression fixture).** 박제된 *입력*. 이 프로젝트에선 PR `.diff` 텍스트와 그 시점의 `terms_v0.1.0.json` (버전 핀 네이밍). `tests/fixtures/` 에 저장.

**스냅샷 (snapshot).** 박제된 *기대 출력*. 어느 시점에 "이게 옳다" 또는 "이 시점의 동작을 박제하겠다" 라고 동의된 도구의 출력. `tests/snapshots/` 에 저장.

**골든 케이스 (golden case).** 픽스처와 스냅샷의 한 쌍. "이 입력에 대해선 이 출력이 정답" 의 박제. v0.2 시작 시 4-5건이 목표.

**회귀 (regression).** 어제 OK 였던 동작이 오늘 깨진 상태. 회귀 픽스처는 회귀를 *조기*에 감지하기 위한 자동 알람.

## 디렉토리 구조

```
tests/
  fixtures/
    pr_945.diff               # PR #945 의 .diff 박제
    pr_922.diff
    pr_923.diff
    pr_1059.diff
    terms_v0.1.0.json         # 박제 시점의 terms_all.json
  snapshots/
    pr_945.json               # 그 PR 처리 후의 결과 (구조화 JSON)
    pr_922.json
    ...
  test_regression.py          # pytest 진입점
```

`tests/` 는 pytest 가 자동 발견하는 디렉토리. `fixtures/` (입력) 과 `snapshots/` (기대 출력) 은 의도적으로 분리한다 — 한 디렉토리에 섞으면 시간이 지나면서 어느 파일이 입력이고 어느 게 기대값인지 헷갈린다.

## 도구

**plain pytest.** 외부 의존성은 `pytest` 하나만 추가 (`uv add --dev pytest`). 스냅샷 비교는 `assert findings == json.load(open(snapshot_path))` 한 줄로 충분하다.

대안 (syrupy, pytest-snapshot 등) 은 픽스처가 20개를 넘어가는 시점에 도입한다. v0.2 단계의 4-5개 픽스처에는 과한 도구이다.

스냅샷 형식: JSON, `sort_keys=True, ensure_ascii=False, indent=2`. git diff 로 봤을 때 한국어가 그대로 보이고, 정렬되어 있어 결정적이다.

## 스냅샷 — 처음부터 JSON, 추출 방식만 진화

> **상태:** 이 절차는 v0.2.0 의 모듈 분리 작업에서 실행되어 완료됐다. 1단계 임시 추출 코드는 제거됐고 현재는 2단계 (정식 반환값 직렬화) 만 유효하다. 이 섹션을 남긴 이유는 같은 패턴을 다른 큰 리팩토링 작업에서 재사용 가능한 템플릿이기 때문.

스냅샷 형식은 처음부터 JSON 으로 통일한다. 모듈 분리 전후로 *형식은 동일*, *추출 방식만* 진화한다. 이 통일이 모듈 분리 작업의 안전성을 검증하는 핵심 메커니즘이다.

### 추출 방식 1단계 — 모듈 분리 전 (임시)

모듈 분리 작업 *시작 전*, `main.py` 끝에 다음 임시 코드를 추가하여 `unmatched` 리스트를 JSON 으로 추출한다:

```python
import sys, json
json.dump(unmatched, sys.stdout, ensure_ascii=False, sort_keys=True, indent=2)
```

이 5줄로 픽스처마다 베이스라인 스냅샷을 박제한다. 1단계는 다음 두 가지 역할을 한다:

1. 모듈 분리 작업 동안 동작이 변하지 않았음을 검증하기 위한 베이스라인.
2. 모듈 분리의 첫 step 인 "print 가 아닌 데이터로 출력" 의 사전 연습.

이 5줄은 모듈 분리가 시작되면 자연스럽게 정식 함수 반환값으로 흡수되어 사라진다.

### 추출 방식 2단계 — 모듈 분리 후 (정식)

`find_terms(parse_diff(diff_text), lookup) → list[Finding]` 의 반환값을 직접 직렬화한다. 임시 추출 코드는 제거된다. 스냅샷 파일은 1단계와 동일한 형식이므로 데이터가 일치해야 한다 — 일치하지 않으면 모듈 분리 작업 중에 의도 외 변경이 발생한 것이다.

### 1단계 → 2단계 검증 절차

1. 모듈 분리 *전*: 1단계 추출로 픽스처마다 스냅샷을 생성하여 commit (`test: 모듈 분리 전 스냅샷 박제`).
2. 모듈 분리 작업 진행.
3. 모듈 분리 *후*: 2단계 추출로 같은 픽스처에 대해 스냅샷을 재생성.
4. diff 검증: 두 스냅샷이 일치해야 한다. 불일치 시 모듈 분리 작업 중 의도 외 변경 발생 — 멈추고 원인 분석.
5. 일치 확인 후 commit (`test: 모듈 분리 후 스냅샷으로 전환`).

이 절차는 큰 리팩토링에서 동작 보존을 검증하는 표준 패턴이다. 다른 리팩토링 작업에도 같은 패턴을 적용할 수 있다.

## 검증 레이어 — 스냅샷 / 유닛

term-consistency 의 회귀 검증은 두 레이어로 나뉜다. 두 레이어는 서로 다른 실패 모드를 잡으며, 서로를 대체하지 않는다.

### 스냅샷 레이어

**위치.** `tests/fixtures/` + `tests/snapshots/`, `tests/test_regression.py` 로 구동.

**무엇을 잡는가.** 실제 PR `.diff` 에 대한 end-to-end 동작. 입력부터 출력까지의 전체 파이프라인이 어제와 동일한가를 검증한다. 진짜 PR 데이터를 쓰므로 합성 입력이 놓치는 실제 조합 패턴을 커버한다.

**한계.** 특정 분기의 축소 효과 — 예: "짧은 용어가 긴 용어 구간에 완전히 포함되면 드롭" — 가 같은 hunk 안에 다른 occurrence 가 있어 보고가 유지되는 케이스에선 스냅샷 diff 가 0 이 된다. 즉 축소가 실제로 일어나는지 스냅샷만으로는 증명할 수 없다. 이슈 #8 fix (PR #21) 에서 드러난 경계.

### 유닛 레이어

**위치.** `tests/test_match.py` (v0.2.0 도입, #8 fix 시 seed 4 케이스).

**무엇을 잡는가.** 개별 함수의 입출력 계약. 각 테스트는 "이 입력에 대해 이 출력이 나와야 한다" 는 최소 단위 계약을 박제한다. 매칭 로직의 변경이 특정 분기의 계약을 깨뜨리면 즉시 드러난다. 합성 입력이라 "왜 이 동작인가" 를 고립된 상태에서 추론할 수 있다.

**적용 범위.** `match.py` 만. `parse.py` 는 4건 스냅샷이 서로 다른 파일 구조를 간접 커버하므로 유닛 중복 투자 안 함. `io.py` 의 네트워크 함수는 mock 유지 부담 대비 수익 낮음. `format.py` 는 현재 dead.

**확장 완료 (v0.3.0 작업 0).** `find_terms` 의 전체 분기 계약 + 헬퍼 (`normalize_ko`, `strip_text`) 경계 + `INCLUDE_SYNONYMS` 훅 (SCOPE 제외 6) 이 박제됐다. 커버리지 확보가 아니라 **계약 고정** 이 의도 — 권위 계층 머지 (v0.3 작업 1-2) 도입 후에도 기존 분기 계약이 동일하게 작동함을 증명하는 안전망이다. 각 테스트의 docstring 에 "어느 분기" / "어느 이슈의 회귀 가드" 가 명시되어, 향후 변경 시 해당 테스트가 깨지면 재검토 대상이 어디인지 즉시 드러난다.

### 두 레이어의 분담

| | 스냅샷 | 유닛 |
|---|---|---|
| 입력 | 실제 PR `.diff` | 합성된 최소 입력 |
| 관측 대상 | 전체 파이프라인 | 개별 분기 계약 |
| 깨지는 신호 | 실제 케이스의 회귀 | 계약 위반 |
| 강점 | 실제 조합 커버 | 경계 케이스 / 축소 효과 |

변경 후 **스냅샷 diff 가 0 이어도 유닛이 깨지면 경계 케이스 회귀**, 반대로 **유닛이 통과해도 스냅샷이 깨지면 실제 조합 회귀**. 두 신호는 서로 다른 액션을 요구한다. 스냅샷 회귀는 실제 데이터와의 괴리, 유닛 계약 위반은 설계 가정의 변화.

## 워크플로 (5단계)

회귀 픽스처가 깔린 후의 표준 변경 절차.

1. **변경 의도 명시.** 어느 이슈를 닫는가, 어느 동작을 어떻게 바꿀 의도인가. PR 본문에 1-2 문장으로 박는다.
2. **변경 적용.** 코드 수정.
3. **테스트 실행.** `uv run pytest tests/`
4. **결과 분석.**
   - 통과: 의도 외 회귀가 없음. 단, 의도한 변경이 *있었어야* 한다면 (예: 매칭 로직 수정) 픽스처 갱신을 빼먹은 것 → 5번으로.
   - 실패: 다음 섹션의 의사결정 트리.
5. **스냅샷 갱신 (필요 시).** 의도한 변경의 결과로 스냅샷이 바뀌어야 한다면, diff 를 사람 눈으로 검토 후 스냅샷 파일을 갱신. 코드 변경과 분리된 별도 commit: `test: <변경 이름> 스냅샷 갱신`.

## 테스트 실패 시 의사결정 트리

테스트가 깨졌을 때 가장 위험한 함정은 **"일단 스냅샷 갱신해서 통과시키기"** 이다. 이 습관이 들면 회귀 픽스처가 죽은 문서가 된다. 매번 다음 트리를 의식적으로 따른다.

```
테스트 실패
   │
   └─ Q1: 이번 변경이 *의도적으로* 출력을 바꾸는 작업이었나?
        │
        ├─ 예 → Q2: diff 가 의도와 *정확히* 일치하나?
        │        │
        │        ├─ 예 → 스냅샷 갱신.
        │        │       별도 commit: test: update snapshot ...
        │        │
        │        └─ 아니오 → 의도 외 변경 발생.
        │                   멈추고 원인 분석.
        │                   원인을 코드에서 찾아 수정 또는 별도 이슈로 분리.
        │
        └─ 아니오 → 회귀 발생.
                   변경을 되돌리거나 원인 분석 후 추가 수정.
                   스냅샷 절대 갱신 금지.
```

**의사결정의 핵심.** "이번 변경이 의도적으로 출력을 바꾸는 작업이었나?" 는 사람만 답할 수 있는 질문이다. 도구는 답할 수 없다. 따라서 회귀 픽스처는 자동화 = "변경이 다른 곳에 영향을 주지 않았는지 자동 검사" 이지, 사람의 *판단을 대체* 하는 도구가 아니다. 사람의 주의를 절약하되 결정은 사람에게 남긴다.

## #9 raw queue → 픽스처 승격 절차

GitHub 이슈 #9 ("판단이 필요한 문제 사례") 는 의심 사례를 모으는 raw queue 이다. 픽스처와의 관계가 명시되어 있지 않으면 #9 는 영원히 raw 로만 남고 회귀 보호로 이어지지 않는다.

### 승격의 5단계

1. **등록.** #9 에 새 케이스 추가. 형식:
   ```yaml
   pr_url: https://github.com/.../pull/N
   file: <path>
   hunk_excerpt: |
     - # ... (영어)
     + # ... (한국어)
   current_output: <도구가 뱉은 알림 요약>
   expected_behavior: <옳은 동작은 무엇인지>
   suspected_cause: <의심 원인. 모르면 "?">
   ```

2. **분석.** 의심 원인이 명확해지면 어느 이슈에 속하는지 분류:
   - 기존 이슈의 새 증상 → 그 이슈에 cross-ref 추가.
   - 새 원인 → 새 이슈 생성, #9 에서 그 이슈로 옮김.
   - 분류 불가 → #9 에 남겨둠 (raw queue 로서의 역할).

3. **픽스처 생성.** 분류된 케이스의 `.diff` 를 `tests/fixtures/pr_<N>.diff` 로 저장. 이미 다른 픽스처와 같은 PR 이면 skip.

4. **스냅샷 박제.** 그 시점 (= 수정 *전*) 의 도구 출력을 스냅샷으로 저장. 일부러 "잘못된" 출력을 박는 것이며, 이슈가 닫힐 때 갱신될 예정이다.

5. **이슈에 cross-ref.** 해당 이슈 본문에 "회귀 픽스처: `tests/fixtures/pr_<N>.diff`, `tests/snapshots/pr_<N>.json`" 추가. 이슈를 닫는 PR 에서 스냅샷이 *함께* 갱신되어야 한다는 명시.

### 라벨링 — GitHub label

#9 의 각 항목은 다음 GitHub 정식 label 중 하나를 가진다:

- `triage-needed` — `suspected_cause` 미정. 분석 대기.
- `analyzed` — 어느 이슈에 속하는지 분류됨. 픽스처 미생성.
- `fixtured` — `tests/` 에 박혔음.

목표는 `triage-needed` 가 빠르게 `analyzed` → `fixtured` 로 흐르는 것이다. `triage-needed` 누적은 분석 백로그가 쌓이는 신호이며, 변경 부채 동시 폭발 패턴의 조기 경보로 본다.

## 어떤 것을 픽스처로 만드는가 — 그리고 만들지 않는 것

픽스처는 적을수록 좋다. 100건의 픽스처는 갱신 비용으로 죽고, 4-5건의 잘 고른 픽스처는 살아남는다.

**픽스처로 만들 것:**
- 이미 분석된 골든 케이스 (PR #945, #922, #923, #1059)
- v0.3 의 권위 충돌 케이스 (training → terms.kr "훈련" vs pytorch-kr "학습")

**유닛 테스트로 가는 것:**
- 알려진 버그의 최소 재현 — 특히 특정 분기의 축소 효과처럼 스냅샷 diff 에 드러나지 않는 케이스. 예: #8 중복 탐지는 실제 4건 스냅샷에서 부분 커버라 fix 전/후 diff 가 0 이었고, 축소 효과는 `tests/test_match.py` 로만 증명된다. 두 레이어의 분담은 "검증 레이어 — 스냅샷 / 유닛" 섹션 참조.

**픽스처로 만들지 않을 것:**
- "비슷해 보이는데 미묘하게 다른" 케이스 다수 → 1건만 대표로 선택
- 같은 버그의 여러 증상 → 1건만
- 1회성 디버그용 케이스 → 디버그 끝나면 삭제

**권장 분량:** v0.2 시작 시 4-6건, v0.3 에 +1-2건 (override 검증), v1.0 진입 시 10건 이하 유지.

## 운영 로그 / 관측성 — 이 문서 범위 밖

도구의 매 실행 단위 추적, 사후 디버깅, API 사용량 모니터링 등의 관측성은 회귀 픽스처와 다른 영역이다. 차이를 정리하면:

| | 회귀 픽스처 | 운영 로그 |
|---|---|---|
| 목적 | 변경 후에도 동작이 같은가 검증 | 매 실행에서 도구가 무엇을 했는지 기록 |
| 결정성 | 결정적 (같은 입력 → 같은 출력) | 매 실행마다 다름 (시각, PR, 결과) |
| 청중 | 자동 비교 | 사람 (디버깅, 사후 분석) |

v0.2 단계 (CLI 한 회 실행, 결과 자체가 출력) 에선 운영 로그가 의미가 약하므로 도입하지 않는다. 운영 로그가 의미를 갖는 시점은 v0.4 (PR 트리거 자동화) 마일스톤이다 — 자동 트리거 시 매 PR 마다 도구가 실행되고, false positive 발생 시 사후 추적이 필요해진다. 자세한 작업은 ROADMAP 의 v0.4 항목 참조.

두 영역을 같은 메커니즘으로 풀려고 하면 양쪽 다 약해진다. 픽스처에 시각/실행 컨텍스트가 박히면 결정성이 깨지고, 운영 로그가 결정성에 묶이면 디버깅이 어려워진다.

## 이 문서를 갱신하는 시점

- 새 픽스처가 추가되거나 폐기될 때 → 디렉토리 구조 섹션 갱신
- 도구 변경 (예: pytest → syrupy) → "도구" 섹션 갱신
- 워크플로에 새 단계가 생기면 → "워크플로" 갱신
- 유닛 테스트 레이어의 스코프가 바뀔 때 → "검증 레이어" 섹션 갱신
- 운영 로그가 v0.4 에서 도입되면 → "운영 로그" 섹션을 별도 문서로 분리하거나 본 섹션 갱신

**드리프트 신호.** 코드에 새 픽스처 파일이 생겼는데 디렉토리 구조 섹션에 안 나옴 → 문서 거짓.
