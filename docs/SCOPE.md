# 스코프 (SCOPE) — v0.1.0

이 문서는 **현재 버전 (v0.1.0) 이 의도적으로 안 하는 일들** 을 명시한다. 미래 버전의 스코프는 [ROADMAP.md](./ROADMAP.md) 에서 다룬다.

각 "제외" 항목은 잠정 결정이다. **언제 다시 검토할지** 가 같이 적혀 있다. 시점이 오지 않았는데 제외 항목을 건드리는 변경이 들어오면, 그 변경은 PR 단계에서 멈춰야 한다.

---

## 도구 한 줄 정의

term-consistency 는 한국어 번역 PR 의 용어를 **terms.kr 의 권장 번역어로 정렬하되, 각 레포의 자체 용어집을 상위 원칙으로 존중하는** 룰베이스 **스크리너** 이다. v0.1.0 은 PyTorchKorea/tutorials-kr 만 대상으로 하고, 레포별 용어집 override 는 v0.x (ROADMAP 참조) 에서 도입한다.

이 한 줄에 들어 있지 않은 모든 것은 **스코프 밖** 으로 간주한다.

### 왜 tutorials-kr 만 — 조직 신뢰의 안전한 출발점

terms.kr 은 pytorch-kr 조직이 직접 운영하는 용어 데이터베이스 프로젝트이다. tutorials-kr 도 같은 조직의 저장소다. 즉 v0.1.0 은 **권위 출처와 적용 대상이 같은 조직 안에 있는** 가장 안전한 조합 위에서 동작한다.

타 한국어 번역 레포로의 확장 (v1.0) 은 이 조직 신뢰가 끊어진 상황을 다루는 단계이다 — 그래서 v1.0 으로 미룬다.

---

## 포함 (v0.1.0이 다루는 것)

- PR `.diff` 텍스트에서 **추가된(`+`) / 제거된(`-`) 주석 라인 (`#` 으로 시작)**
- 그 hunk 안에서 영어 term 의 단어 경계 매칭 (`\b`, case-insensitive)
- 매칭된 term 의 한국어 번역어 (terms.kr 의 `meanings[].korean`) 가 동일 hunk 의 한국어 텍스트에 있는지 확인
- 한영 병기 패턴 (`한국어(english)`) 매칭
- unmatched 케이스의 영문/한글 컨텍스트 출력

---

## 제외 (v0.1.0 이 *의도적으로 안 하는* 것)

각 항목은 "이건 도구의 일이 아니다" 또는 "지금 단계에서 다루기엔 가설 검증 비용이 크다" 는 판단의 결과다.

### 제외 1. 1차 한영 번역의 정확도 자체

**무엇.** 영어 원문이 한국어로 *의미적으로 올바르게* 번역되었는지 검증하지 않는다. 도구는 "영어 term → 정해진 한국어 번역어" 의 1:1 매핑만 본다.

**왜 제외.** 의미 검증은 LLM 또는 번역 평가 모델이 필요하다 → 원칙 1 (가볍다) 위반. 또한 가설 ("리뷰어 부담 경감") 의 핵심이 아니다 — 의미 검증은 사람 리뷰어가 가장 잘 한다.

**이로 인해 빠지는 케이스.** 영어 원문과 의미가 완전히 다른 한국어 번역이 와도, 용어 매핑만 맞으면 통과한다. 예: "dropout 은 학습을 돕는다" 가 "드롭아웃은 학습을 방해한다" 로 번역되어도 도구는 통과시킴.

**다시 검토할 시점.** 없음. 이 도구의 영구 비스코프.

---

### 제외 2. 한국어 → 한국어 수정 hunk

**무엇.** 한 hunk 안에서 `removed`/`added` 가 모두 한국어인 경우 (= 기존 번역의 *수정*). 도구는 영어쪽 텍스트에서 영어 term 을 찾고 시작하므로, 영어가 아예 등장하지 않으면 매칭 시도 자체를 안 한다.

**왜 제외.** v0.1 은 **"1차 한영 번역은 이미 잘 된 상태로 PR 에 들어온다"** 는 가정 위에 선다 (아래 "테스트되지 않은 가정" 섹션 참조). 한국어 수정은 그 1차 번역 *이후* 단계의 작업이고, 도구의 가설 ("PR 제출 전 룰베이스 스크리너가 리뷰어 피로를 경감") 의 주된 청중이 아니다.

**이로 인해 빠지는 케이스.** 1차 번역에선 잘 잡혔다가 한국어 수정 단계에서 잘못된 용어로 바뀌는 시나리오. 예: 어떤 hunk 에서 "혼합 정밀도" 가 다른 표현으로 교체되는 수정이 들어와도 도구는 알리지 않음.

**다시 검토할 시점.** v1.0 (도구 공개) 시점에 실제 사용자/리뷰어 피드백이 들어오기 시작하면 그 시점에 재평가. 그 전까지는 유지보수자 직접 확인을 근거로 가정 유지. 외부 피드백 전까지 SCOPE 안으로 옮기지 않는다.

---

### 제외 3. 코드블럭 / 인라인 코드 안의 내용

**무엇.** 백틱(`` ` ``) 으로 감싸인 영역과 트리플 백틱 코드블럭의 *내용* 자체. 이 영역은 매칭 전에 strip 된다.

**왜 제외.** 코드는 번역하지 않는다 (tutorials-kr 번역 가이드라인). 코드 안의 영어 식별자 (`model.conv1.weight`) 를 용어 매칭에 넣으면 거의 전부가 false positive 가 된다. 원칙 2 (FP > FN) 는 "의심되면 알린다" 지만, "코드는 절대 번역 대상이 아니다" 는 안전한 사전 컷이다.

**이로 인해 빠지는 케이스.**
1. 원본에서 코드/식별자에 백틱을 안 씌운 케이스. 예: `` model.conv1.weight `` 가 그냥 `model.conv1.weight` 로 적혀 있으면, "model" 같은 일반 단어가 용어 매칭에 잡혀버림. 이건 데이터(원본)의 문제이지만 우리쪽엔 false positive 로 보임.
2. 주석 안에 코드 식별자가 백틱 없이 박혀 있는 경우.

**다시 검토할 시점.** v0.2.0 회귀 픽스처에 백틱 누락 케이스가 명시적으로 들어가면 (= 데이터 측 문제로 분류), 도구 측의 책임 범위를 그때 재정의.

---

### 제외 4. 오타 / 띄어쓰기 / 맞춤법

**무엇.** 한국어 맞춤법, 띄어쓰기, 오타 검사.

**왜 제외.** 이슈 #4 에서 "별도 도구로 분리" 결정. 용어 일관성과 맞춤법은 다른 종류의 검사이고, 묶으면 두 도구 모두 무거워진다.

**이로 인해 빠지는 케이스.** 용어는 맞지만 띄어쓰기가 틀린 경우. 예: "혼합정밀도" (붙여쓰기) — `normalize_ko` 가 공백을 무시하므로 도구는 통과시킴. 이건 의도된 통과.

**다시 검토할 시점.** 없음. 별도 도구로 분리 확정.

---

### 제외 5. 번역 가이드라인의 비-용어집 규칙

**무엇.** tutorials-kr/TRANSLATION_GUIDE.md 에 적힌 규칙 중 "용어 매핑이 아닌" 것들. 예: "제목은 명사형으로", "존댓말 사용", "수동태 지양" 등.

**왜 제외.** 가이드라인 규칙들은 자연어로 적혀 있어 룰베이스로 옮기는 비용이 크고, 일부는 LLM 없이는 검증 불가 → 원칙 1 위반 위험. 이슈 #3 에서 "LLM 으로 가이드라인 생성" 을 별도 마일스톤으로 분리한 이유.

**이로 인해 빠지는 케이스.** 용어는 정확하지만 문체 규칙을 어긴 번역.

**다시 검토할 시점.** v1.0 (이슈 #3 마일스톤). v0.x 동안은 영구 비스코프.

---

### 제외 6. 같은 용어의 동의어 (synonyms) 매칭

**무엇.** terms.kr 용어집의 `meanings[i].synonyms` 리스트는 현재 매칭에 사용되지 않는다. 오직 `meanings[i].korean` 만 본다.

**왜 제외.** v0.1 베이스라인 단순성 + **synonyms 의 권위적 위치가 운영자 의도상 불명확**. terms.kr 측이 "synonyms 도 동등 인정" 인지 "비권장 대안" 인지 정하지 않은 상태에서 도구가 임의로 동등 인정하면 도구의 정확도 정의가 흔들린다. 보수적으로 무시.

**이로 인해 빠지는 케이스.** 용어집에 `korean: "활성화 함수", synonyms: ["활성 함수"]` 로 있을 때, 번역자가 "활성 함수" 로 옮긴 케이스. 도구는 이를 unmatched 로 알림 (= false positive 의 한 형태).

**다시 검토할 시점.** terms.kr 운영자에게 synonyms 의 권위적 위치를 직접 확인한 후. 또는 v0.2.0 normalize_ko 비대칭 수정 작업과 같은 PR 에서 같이 검토 — 두 변경 모두 "한국어 텍스트와 허용 목록의 비교 로직" 을 건드리므로 묶는 게 자연스럽다.

---

### 제외 7. 레포별 용어집 override (v0.1.0 미구현)

**무엇.** 현재 v0.1.0 은 terms.kr 만을 권위로 사용한다. 각 한국어 번역 레포 (예: pytorch-kr) 가 자체적으로 운영하는 용어집은 **참조하지 않는다.**

**왜 제외 (잠정).** v0.1 베이스라인 단순성. 권위 계층 구조를 도입하면 매칭 결정 로직이 복잡해지고, 그 복잡도를 회귀 픽스처로 잡을 준비가 안 되어 있다. 모듈 분리와 픽스처가 깔린 다음 단계의 일.

**이로 인해 빠지는 케이스.** terms.kr 와 레포별 용어집이 **충돌하는 경우, 레포별 용어집이 정답인데 도구는 terms.kr 기준으로 unmatched 알림.** 예: "training" 에 대해 terms.kr 는 "훈련", pytorch-kr 은 "학습" → 번역자가 "학습" 으로 옮긴 PR 을 도구가 잘못 알림 (false positive).

**다시 검토할 시점.** v0.x (TBD, ROADMAP 참조). 이 항목이 도구 본래 의도의 핵심이므로, **PR 트리거 (#11/#12) 와 v1.0 (타 레포 확장) 보다 먼저 닫혀야 한다.** 자동화 (PR 트리거) 가 먼저 깔리면 false positive 가 PR 댓글로 도배되어 도구의 가설 자체가 망가진다.

> **이 제외는 다른 제외 항목들과 성격이 다르다.** 다른 제외는 "안 하기로 한 일" (영구 또는 잠정 비스코프) 이지만, 이 항목은 **"해야 하는 일이지만 아직 못 한 일"** 이다. 도구의 본래 정의의 절반. 이걸 영구 침묵으로 분류하지 말 것.

## 테스트되지 않은 가정 (Untested Assumptions)

이 가정들은 v0.1 의 설계 전제이지만 데이터로 검증된 적은 없다. 이 중 하나가 깨지면 위 스코프가 흔들릴 수 있다.

### 가정 1. 1차 한영 번역은 이미 잘 된 상태로 PR 에 들어온다

**전제로 하는 결정.** 제외 2 (한국어→한국어 수정 hunk).

**깨지는 신호.** v1.0 도구 공개 후 외부 리뷰어/사용자로부터 "한국어 수정 단계에서 용어가 깨지는 케이스" 가 반복적으로 들어옴.

**검증 시점.** v1.0 도구 공개 + 외부 피드백 누적 후. 그 전까지는 유지보수자 직접 확인을 근거로 유지.

---

### 가정 2. 코드 식별자에 백틱이 안 씌워진 케이스는 드물다

**전제로 하는 결정.** 제외 3 (코드블럭 strip).

**깨지는 신호.** 회귀 픽스처 안에서 백틱 누락이 false positive 의 주요 원인으로 잡힘.

**검증 시점.** v0.2.0 회귀 픽스처 작성 단계.

---

### 가정 3. 각 한국어 번역 레포에는 (대부분) 자체 용어집이 존재한다

**전제로 하는 결정.** 도구 정의의 "각 레포의 자체 용어집을 상위 원칙으로 존중" 부분, 그리고 v1.0 (타 레포 확장).

**가정 형태.** 대부분의 한국어 번역 문서 프로젝트는 "용어 → 한국어 번역" 의 1:1 매핑 문서를 자체적으로 운영한다. 형태는 마크다운으로 작성된 flat dict (사람이 직접 검토하는 용도이므로 풍부한 구조는 아님). pytorch-kr 의 경우 이미 확인됨.

**깨지는 신호.** 타 레포 확장 시점에 "용어집이 없는" 또는 "전혀 다른 형태로 운영되는" 레포가 다수.

**검증 시점.** v1.0 마일스톤 진입 전, 후보 레포 3-4 개의 용어집 형태를 직접 확인.

---

### 가정 4. terms.kr 의 `meanings[].korean` 이 권장이고 synonyms 의 권위적 위치는 미정

**전제로 하는 결정.** 제외 6 (synonyms 매칭).

**가정 형태.** synonyms 는 "허용" 인지 "비권장 대안" 인지 운영자 의도가 불명확. 따라서 v0.1 은 보수적으로 무시.

**깨지는 신호.** terms.kr 운영자가 "synonyms 는 동등 인정" 또는 "비권장" 의사를 명시.

**검증 시점.** terms.kr 운영자 연락 시점. 운영자 피드백이 필요한 사항으로 분류된다.

---

## 이 문서를 갱신하는 시점

다음 중 하나라도 발생하면 SCOPE.md 를 다시 본다:

- 새 버전 릴리즈 (vX.Y.Z 표기 갱신 + 제외 항목 재검토)
- 위 "테스트되지 않은 가정" 중 하나가 깨졌다는 데이터가 나옴
- 새로운 제외 항목이 추가되거나 (= 의도적 비탐지를 새로 결정함) 기존 항목이 스코프 안으로 들어옴
- 제외 7 (레포별 용어집 override) 이 닫힘 (= 도구 본래 정의의 절반이 완성됨)

PR 본문에 SCOPE.md 변경이 같이 들어가야 한다 — 코드만 바꾸고 SCOPE 가 그대로면 둘 중 하나는 거짓이다.
